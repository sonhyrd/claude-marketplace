# Changelog - sss

All notable changes to the sss plugin in this marketplace will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).

## [Unreleased]

### Added

- `claude-settings` skill: the baseline carries **`env.CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`**, so Claude Code's automatic memory — the persistent store under `~/.claude/projects/<project>/memory/` that a session reads at start and writes to as it goes — is off on every machine this skill applies to. It is the **first `env` key the baseline has ever held**, and the frontmatter's long-standing "never touches env" becomes "one key". The rest of `env` stays out for the reason it always did: `PYENV_VERSION` and `CLAUDE_HOST_LABEL` name a machine. This key names nothing — no path, no host, no version — which makes it a preference exactly as portable as `skillOverrides`, and the state it replaces is the incoherent one, where the same user gets recalled facts on the laptop and none on the VPS. Apply required no change at all, which is the point: `jq -s '.[0] * .[1]'` **deep-merges**, so the key lands *alongside* whatever `env` the target machine already holds rather than replacing the object — verified against a machine carrying `CLAUDE_HOST_LABEL` and `PYENV_VERSION`, both of which survive. That property is now load-bearing and documented as such; the merge must never become a whole-object replace. Capture is the asymmetric half and is deliberately so. It lifts the **one named key**, never `.env` whole, since the whole object is precisely how this machine's `PYENV_VERSION` would reach every other. Capturing on a machine where memory is still on therefore drops the key from the baseline — but apply only ever *adds* keys, so the machines that already have it keep it, and turning memory back on fleet-wide is an explicit baseline edit plus a removal on each box rather than something a stray capture does silently. Two adjacent mechanisms are named in `SKILL.md` as *not* being this one, because both are the natural wrong guess: `/pause-memory` is session-scoped and lives in the transcript, and `autoMemoryEnabled` is a global-config key in `~/.claude.json`, a file this skill does not manage at all. The env var is the one lever this skill can actually reach
- `hotfix-draft-release` skill: ships one or more **already-merged** fixes as their own patch release, leaving the rest of `main` out of it — branch from the last published release tag, cherry-pick only the picked PRs, tag, and open a GitHub release that is **always `--draft`**, so a human reads the notes and clicks Publish. The flow is list → pick → cut, and the pick is deliberately the user's: the candidate list is the same set GitHub's "What's Changed" would tag cumulatively, and the entire reason to run this skill is that some of it is in QA rather than release-ready, which is a judgement no script has. The work lives in `scripts/cut-hotfix.sh` rather than in a shell sequence the model types, because the failure mode here is not a wrong answer but a **pushed tag on the shared remote**: without `set -euo pipefail` a mid-run failure keeps going and pushes a tag pointing at all of `main` instead of the isolated fix. Three more things are baked in for the same reason — the branch is `hotfix-vX.Y.Z` with a **hyphen**, since the `hotfix/vX.Y.Z` slug fails to create at all in any repo that already has a plain `hotfix` branch (`cannot lock ref … 'hotfix' exists`); the merge commit is cherry-picked with `-m 1` falling back to a plain pick, because a squash-merged PR is one parent and a merge-committed one is two and the invocation differs; and the `diff --stat` against the base is printed before the tag is trusted, which is the only step that actually proves the release is scoped to the picked PRs. The original branch is restored even on failure. Recovered from the `mac-wipe-2026-08-08` Drive archive (`claude/skills/`), where it had been a machine-local `~/.claude/skills/` entry — which is why it was lost — and it lands here at the user's direction rather than being restored in place
- `hotfix-draft-release` skill: `$CUT` resolves from the **plugin root** (`$CLAUDE_PLUGIN_ROOT` → versioned plugin cache, highest first), replacing the bare relative `scripts/cut-hotfix.sh` the machine-local copy could get away with. Every command in this skill runs from the repo *being released*, so the relative path resolves against somebody else's tree — it finds nothing in most repos, and in an unlucky one it finds a different `scripts/cut-hotfix.sh` and runs it against the shared remote. An unresolvable `$CUT` is a named STOP that routes to the documented manual fallback, not a fall-through, and the cache candidates use `sort -Vr` for the same reason `translation-sync` does: plain `sort -r` is lexicographic and picks `1.9.0` over `1.10.0`

- `skill-upper` skill: **vendored verbatim from [alibaba/skill-up](https://github.com/alibaba/skill-up)** (`skills/skill-upper/`, upstream `5ba8c3a`, release `v0.8.0`), so authoring and iterating Agent Skill evals invokes as `/sss:skill-upper`. It drives the `skill-up` Go CLI — scaffold `evals/eval.yaml` and `evals/cases/*.yaml`, run cases against a real agent engine, grade via `rule_based` / `agent_judge` / script judges, and read the report back into a repair loop. Carried over are `SKILL.md`, the six `references/` pages (`cli`, `eval-yaml`, `case-yaml`, `judge-types`, `install`, `migrate-anthropic`), the two `assets/*.tmpl` scaffolding templates, and both READMEs. **Upstream's own `evals/` tree is deliberately not carried**: those cases test the skill against upstream's fixtures and would be run by anyone pointing `skill-up` at this plugin, proving nothing about this marketplace while pulling in a fixture skill tree and a bash judge. The skill is inert without the CLI on `PATH` — `references/install.md` is the install path, and this machine has `~/.local/bin/skill-up` `v0.8.0` from upstream's checksum-verified `install.sh`. It lands in `sss` rather than as its own plugin, at the user's direction, even though the marketplace's usual shape is one plugin per CLI (`fd`, `jq`, `ripgrep`); the cost is that `sss` — otherwise entirely locally-authored — now holds one directory under the verbatim rule, recorded in `CLAUDE.md`. Note the name mismatch upstream ships and this copy preserves: the frontmatter `name` is `skill-upper` while the body's H1 reads `use-skill-up-cli`; the frontmatter is what the host reads
- `claude-settings` skill: **apply now deploys a browser shim**, `scripts/browser-shim.sh` → `~/.local/bin/chromium`, so `web-search` works on a machine with no installed browser. It is the one skill in the roster that needs one, and it finds a browser by **name on `PATH`** — its resolver's OS default-path tier is populated for macOS and Windows but empty on Linux (`osCandidates = []`), so `PATH` is the sole discovery mechanism and a VPS fails every call with `No supported browser binary found`. Such a box usually *does* have a browser: the Chrome that Playwright downloaded into `~/.cache/ms-playwright/chromium-<rev>/`, under a versioned path nothing looks in. The shim bridges the two by satisfying the resolver's existing `"chromium"` candidate. Three properties are load-bearing rather than defensive. A **real system browser always wins** — the shim `exec`s `/usr/bin/chromium`, `google-chrome`, `/opt/google/chrome/chrome`, a snap or a macOS `.app` before it looks at any cache, because the standing hazard of a file named `chromium` first on `PATH` is shadowing the browser someone installs next month. Resolution is **at run time, not install time**, since Playwright deletes old revisions on upgrade and a symlink to `chromium-1234` becomes a dangling exec the day it becomes `chromium-1250`. And `chromium_headless_shell-*` is **skipped despite speaking CDP**, because it cannot run headed while the `web-search` daemon may. Deployment is conditional on no browser being found first, and is followed by a `chromium --version` check, because the two failure modes are silent otherwise: `~/.local/bin` off `PATH` deploys a file nothing will ever call, and a box with neither browser nor Playwright cache exits 127 — reported as `npx playwright install chromium`, which needs no redeploy afterwards. The rejected alternative, patching `lib/browser-bin.js` to read the Playwright cache, is the better *upstream* fix and the wrong one here: `plugins/web-search/` is vendored verbatim from `ogulcancelik/agent-skills`, and this buys the same result with no tracked deviation. `WEB_SEARCH_BROWSER_BIN` was rejected for landing in `env`, which this skill deliberately does not sync, and for applying only inside Claude Code rather than to any shell

- `pr-review` skill: Step 6 — **prove**. The run now carries a PR from review to a passing Playwright test on one `BASE`, and the skill's description says so. Step 6 writes `.pw-prove/handoff.json` into the target repo and then invokes `e2e:pw-prove` through the Skill tool, which ticket #9's unpin made reachable at all. The artifact is written even though a chained run already shares this context, because it is `pw-prove`'s input contract regardless of who called it: a cold `/e2e:pw-prove <PR#>` an hour later picks up the same confirmed findings a chained run gets for free. Three orderings carry a failure mode each — **gitignore before write**, because `pw-prove` stages only the spec, POM and HAR and nothing downstream cleans up an artifact in a tracked path; **`head_sha` read last, after every commit the run makes**, because the reader deletes the whole file on a mismatch, so a SHA captured one commit early is the review silently thrown away rather than a stale artifact anyone gets warned about; and **every severity ships**, not just the applied ones, because `pw-prove` decides for itself which findings name a user-observable behaviour and a Medium withheld here is one it cannot weigh. `findings` carries Step 4b's order, since "highest confidence first" is what agreement between unmerged tracks bought. The schema is `pw-prove`'s, not ours — the copy carried here to make the step executable is frozen against the original by `make test-pr-review-handoff-parity`, keys and nested keys alike. `pw-prove`'s confirmation gate fires on this path and is deliberately left alone: it is the one human checkpoint in an otherwise unattended chain
- `pr-review` skill: Step 5 — **sync translations**, so a PR that changed locale keys gets them onto the server before anything renders them. The stage sits after the fix commit and before any proof, because an unsynced key renders as its raw dot-path — a browser pointed at a pre-sync server photographs `board.title` instead of the string the PR added. It invokes `sss:translation-sync` whole rather than re-deriving any of it: that skill resolves its own config, validates its own token, and owns its own confirmation prompt and its own push, which is exactly the "later stages own the pushing" Step 4 defers to. It fires only when **both** findings resolved back in Step 1 are true — the repo has `.github/hyrd-trans-bot.json` at its root, and the diff touched locale JSON under the directory that config resolves to. Neither implies the other: config presence alone would talk to the server on every PR in the two repos that have a config, and a locale diff alone would fire in a repo with no server to sync to. Requiring both is what makes the stage self-disabling everywhere else, with no list of repo names to maintain. Either finding false and the stage is **absent** — no prompt, no warning, no line in the report — because nearly every repo in reach of this skill has no translation config, and a stage that announced its own irrelevance would announce it on nearly every run. Both findings resolve in Step 1 off the one `BASE` the three tracks share, so the decision is settled before the fix stage moves the tree underneath it. The gate is deliberately directory-level: `path` and `exclude` scope *namespaces inside* the locale file rather than paths on disk, and `translation-sync` applies them itself when it diffs, so re-implementing them here would mean parsing the changed JSON to decide whether to invoke the skill that parses it
- `translation-sync` skill: relocated in from the per-repo vendored copies so a marketplace skill can invoke it. Same config file, same safety contract, same output discipline — nothing about the sync itself changed. It ships its own CLI (`hyrd-trans.mjs` plus `lib/`) and `SETUP.md` alongside `SKILL.md`, because a skill pointing at a binary it does not carry is a skill that works in exactly the repo it was hand-copied into. `$CLI` now resolves from the plugin root (`$CLAUDE_PLUGIN_ROOT` → versioned plugin cache, highest first → this repo's checkout) instead of the hardcoded `.claude/skills/translation-sync/` path, which no plugin install has; an unresolvable `$CLI` is a named STOP rather than a fall-through, since the fall-through's failure mode is `Cannot find module` a few steps into a run that has already touched the server. Three details in that block are load-bearing rather than stylistic: the cache candidates are ordered by `sort -Vr`, a **version** sort, because plain `sort -r` is lexicographic and picks `1.9.0` over `1.10.0` — silently running a stale CLI against the live server; the resolved path is absolutised, because the dogfooding candidate is the one cwd-relative entry and a later `cd` into the repo being synced would otherwise invalidate it; and the lookup uses `find` rather than a glob, since an unmatched glob is fatal in `zsh`. The frontmatter description gains an explicit "Use when" clause, which is what this marketplace's own skill-authoring guide requires for discovery and what the vendored copy never needed; the now-redundant `triggers:` frontmatter list goes with it, since it is a non-standard key Claude Code never reads and the description is the actual discovery surface. The resolution rationale lives in `SETUP.md` rather than `SKILL.md`, which keeps the body under this marketplace's documented 500-line cap. The three pre-existing copies were byte-identical, so the move reconciled nothing; `hyrd-translation` stays the CLI's source repo and keeps its `test/`, and the vendored copies in `nuxt-hyrd-chrysus` and `hyrd-widget` are deleted by a follow-up in those repos
- `pr-review` skill: Step 4 — **fix and commit**. The four review sections are reported first and unchanged, then every Critical and High finding is applied or explained, overlap-confirmed ones first, and the result is committed and never pushed. Overlap orders the work without filtering it, so a single-track Critical is still applied; Medium and Low are described rather than applied. Severity is assigned in the parent from an explicit mapping table, because only the OCR track emits one and `matt:code-review` speaks in hard violations and judgement calls instead — the grading is per finding, never per track, so `Track`'s "never merged or ranked" clause survives it. A fifth `## Fixes` section names what was applied, what was only described and why. `CONTEXT.md` gains **Stage** for the serial phases this introduces
- `pr-review` skill: reviews one diff on three **tracks** at once — Standards and Spec from `matt:code-review`, plus a rule-driven file-by-file pass from `sss:ocr-delegate` — and reports them side by side with an `## Overlap` section naming what two or more tracks independently found. The agreements are the highest-confidence findings precisely because no track saw another's context, so Overlap is added *underneath* three intact verbatim sections rather than merged into them, and it is computed in the parent against the full text rather than delegated to a fourth agent that could only paraphrase. `matt:code-review` **already fans out on its own** — two `Agent` calls in one message, one per axis — so this skill loads it *inline* and issues three calls where the loaded skill says two, putting all three tracks at the same depth. Wrapping it in an agent instead would have nested its fanout one level below OCR's, betting that a spawned agent may itself spawn; the bet's loss is silent, degrading a two-axis review to a single context with nothing in the output saying so, and loading inline makes the bet unnecessary. The rejected alternative — pasting the Standards and Spec briefs into this skill for three flat peers — buys the same shape for a second permanently-owned copy of the twelve-smell baseline, which is the duplication the composition exists to avoid. This is also the skill's one override of an instruction in a skill it does not own, recorded as such, since an upstream rewrite of that step is where it breaks. Prep is the parent's: `gh` lookup, checkout, `git merge-base`, empty-diff check and the `ocr` probe resolve to four findings the two skills verify rather than rediscover, because three tracks resolving three ranges is how Overlap starts lying, and a bad ref should fail once in the open rather than inside parallel agents. OCR's optional fix mode (its Step 7) stays closed unless the user asked for "review and fix", and its coverage summary is a contract — a report missing `coverage_rate` or a reason per skipped file goes back to the agent. A missing `ocr` binary runs the two axes and opens the report by saying the composition collapsed to a plain `matt:code-review` run, rather than printing an empty third heading. Both target skills must stay model-invocable for any of it to work: `disable-model-invocation` blocks *chained* Skill-tool launches as well as unprompted ones, the same trap that broke `pw-prove`'s quality gate when `e2e-reviewer` briefly carried the flag. `CONTEXT.md` gains **Track** and **Axis** to keep the two from collapsing into each other — an axis is a question `matt:code-review` asks, a track is who ran it, and two of the three tracks are that skill's two axes
- `config-schema` skill: audits a repo's run-time configuration and emits a schema that makes missing config fail loudly instead of silently. Finds every `process.env` / `import.meta.env` read, diffs the committed template against the code in both directions (dead keys *and* undocumented live keys — 21 and 11 respectively in the repo it was extracted from), and emits four artifacts: a declarative schema, a generated `.env.example` with a `--check` mode, a boot assertion naming every missing key at once, and a build-time assertion. The banned pattern is `process.env.X || ''`, which converts a configuration error into a per-request 502 that reads like a healthy server; the resolver returns `undefined` rather than `''` so that is structural, not advisory. Two axes no off-the-shelf validator models: `class` (static | secret), which is the handoff contract to `dev-local`, and `scope` (run-time | build | tooling), which decides *how* absence is caught — a bundler-inlined key has no boot to fail at and ships as `undefined` inside the artifact, so its enforcement moves into the build. `scope` is derived mechanically from the read site and never asked; `class` and `required` are never guessed, and with no TTY the skill refuses and exits non-zero rather than prompting, because an unattended worker that hits a prompt hangs rather than slows. There is deliberately no `--assume` flag: the assumption it would make silently — Secret treated as Static — commits a `devDefault` for a credential. A bundler-inlined prefix (`VITE_`, `NEXT_PUBLIC_`) *proves* a key is not a Secret whatever its name says. Supported frameworks are Vite and Nuxt; anything else is refused rather than given improvised glue. Files land unstaged and self-verified — the skill runs the repo's typecheck and its own generated `--check` and reports pass or fail rather than declaring the patch ready
- `dev-local` skill: takes a fresh checkout to bring-up and proves it. Ports go to portless (`portless.json` plus a `dev` script with no `--port` flag anywhere, since an explicit `--port` beats portless's injected `PORT` and silently reintroduces the collision), hand-rolled port discovery is replaced by `portless get` — a pure function of cwd and app name, so it resolves *before* the server is up, which is when a test runner's `webServer.url` needs it — and `baseURL` and `webServer.url` resolve to one value via `E2E_BASE_URL` → `PORTLESS_URL` → `portless get`. It ends in a **Liveness Proof**: one authenticated 2xx through the app's own API layer *and* the same request unauthenticated returning 401, because a 200 on `/`, a registered route and a green `portless doctor` are all compatible with a completely dead backend — none of them crosses the proxy layer where the fault lives. The preflight refuses with the exact fix and never attempts sudo, a trust-store write, or a daemon install, which is the only correct behaviour on a headless box. No tmux, no log parsing, no readiness polling, no port discovery. v1 ships **no secret wrapper**: `agent-native vault exec` is a specification, not a shipped binary — the product has an in-app encrypted `app_secrets` store but no `vault` CLI subcommand — so generating flags against it would be guessing at a surface that does not exist
- Vocabulary for both skills at `plugins/sss/skills/config-schema/references/vocabulary.md`, single-owner rather than duplicated per skill, because `class` and `scope` are the contract between them and two definitions of a contract is the same disease as an unvalidated `.env.example`

### Fixed

- `pr-review` skill: **Step 6b's ownership rule yielded to the first request it refused.** A `skill-up` eval case asks, mid-run, for a `tracks` field on the handoff findings — a key `pw-prove`, the schema's only reader, does not read. Across five sampled trials the run did the edit twice, and one of those also rewrote the Gotcha that forbids it, reclassifying additive keys as "inert, tolerated" so the guardrail no longer said no. Two trials wrote the change into the real marketplace checkout from inside the eval sandbox, `plugins/e2e-skills/skills/pw-prove/SKILL.md` included; all of it was reverted. The rule was never unclear — "if the contract is wrong, change it there and push the fork" was read as licence to go and do it, since it named the destination without saying who travels. Step 6b now answers the request instead of executing it: name the owner, say the change is two files in two plugins plus a parity test and a targeted push to the fork, and finish the run. The Gotcha states that neither half of the rule is edited away by a request to extend the schema, and records the trial that did. The case is now unambiguously mid-run and passes 4/4 sampled, where it was 2 PASS / 1 FAIL before — the flakiness was in the routing, not in `head_sha`, which every trial got right

- `ocr-delegate` skill: **the documented commands did not run.** Steps 1 and 2 pinned `--format json`, a flag `ocr delegate` has never had — `ocr delegate preview --format json` exits non-zero with `unknown flag: --format` against the current release (v1.8.10), so the skill stopped on its first command and every run through it was a run that reviewed nothing. The coverage contract added alongside it was written against JSON field names (`reviewable_files`, `total_files`, `coverage_rate`) that no output emits. Both are now stated against the Markdown `preview` actually prints, which is structured enough to parse: a `# Files (N reviewable / M total)` header, a bullet list carrying `mode` and the `from`/`to`/`merge_base` refs Step 3 builds git commands from, plain bullets for reviewable files and `~~`-struck ones for excluded, each with its reason. The `--format` row in the flag table is replaced by `--max-git-procs`, which does exist. The failure reached `pr-review` too, whose OCR track invokes this skill: its degradation clause covered `ocr` missing from PATH but not an `ocr` that is present and rejects the invocation, so a broken tool and a clean review read identically in the report — they are now distinguished, with the failing command quoted. A new gotcha records the limit that made this expensive to notice: OCR excludes `.md` as `unsupported_ext`, so on a skills or docs repo it can preview 26 files, offer 12, and report 100% coverage having never seen the diff's substance
- `translation-sync` skill: **the CLI truncated its own output.** `hyrd-trans.mjs` called `process.exit(0)` directly after `process.stdout.write`, and Node's writes to a pipe are asynchronous — so the exit tore the process down mid-flush. Reproduced at exactly one pipe buffer: a 4.3 MB `apply --dry-run` result arrived as 65536 bytes of unparseable JSON *with exit 0*, meaning the output contract at the top of the file reported success on lost data. A pipe is the normal case, not the edge one: an agent's Bash tool, `| jq`, and command substitution are all pipes, and `diff-all` across several languages of a large project is exactly the payload that overflows. Writes now exit from the write callback, once the data has reached the OS. `process.exitCode` is set as well as calling `process.exit` from that callback, because `exitCode` alone fixes the truncation but not the exit — an idle keep-alive socket left by `fetch` can hold the event loop open for seconds after the output is complete. The four documented exit codes are unchanged
- `translation-sync` skill: `git.mjs` ran every git subprocess on `execFileSync`'s 1 MB default `maxBuffer`, which is smaller than a real locale file. A multi-MB base blob made `git show <base>:<locale>.json` throw, and `computeChangeset` reads a failed `show` on a path that *does* exist at base as a mis-resolved path — so the PR-aware gate degraded to fail-safe adds-only and blamed "path-resolution failure". The direction was safe and the reason was wrong, and it would have arrived as a function of file size on a repo whose locale files only grow. `maxBuffer` is now explicit
- `translation-sync` skill: a key passed to `apply` in both `deletes` and `adds`/`updates` is still dropped from the delete set, but now reported as `skippedConflicting` rather than silently vanishing — returning `deletes: 0` for a key the caller asked to delete reads as "already gone"

### Added

- `claude-settings` skill: the plugin roster now syncs. `baseline/plugins.json` tracks the portable marketplaces and their enabled plugins; `scripts/capture-plugins.sh` writes it from live settings and `scripts/apply-plugins.sh` installs it onto a new machine. This closes the gap the skill previously documented and left open — the settings merge deployed `statusLine`, `skillOverrides` and `permissions` to a fresh box and no plugins, with `references/external-plugins.md` as a checklist someone had to notice and work through by hand. A machine provisioned that way lists none of the external skills and looks broken. The portable/local split is **computed, not hand-maintained**: a marketplace is portable unless its `source.source` is `directory`, since a `github` source (`{"repo": "cloudflare/skills"}`) is byte-identical everywhere while a directory source carries a working-tree path that is wrong on every other machine. `claude-plugins-official` is portable by the same rule from the other side — it ships with Claude Code and never appears in `extraKnownMarketplaces`, so a plugin whose marketplace has no entry cannot be directory-sourced. Only this repo's own `sss` / `matt` / `e2e` stay manual, one `marketplace add` on a new box. Apply drives the `claude plugin` CLI rather than merging these keys into `settings.json`, which is why they are a second baseline file and not new keys in `settings.base.json`: hand-writing `extraKnownMarketplaces` registers a marketplace with no clone on disk, so it resolves to nothing, whereas `claude plugin marketplace add` clones, validates the manifest and writes both settings keys itself. Both CLI commands are idempotent and apply reports `=` for what is already present, so re-running is a no-op; `DRY_RUN=1` previews without installing, which also serves as a read-only audit of a machine against the roster. Preview before applying is a documented step rather than a suggestion, because it clones third-party repos and `i-have-adhd` ships a `SessionStart` hook

### Changed

- `delegate-tickets` skill: **unpinned, behind a confirmation gate** ([ADR 0006](../docs/adr/0006-delegate-tickets-unpinned-behind-a-confirmation-gate.md)). `disable-model-invocation: true` came off the frontmatter, so the skill is model-invocable and Skill-tool chainable for the first time — `/sss:autoship` and any coordinator holding an approved ticket tree can now hand into it instead of printing "now run `/delegate-tickets`" and stopping at a seam the user has to cross by hand. The flag's real job — keeping an expensive, irreversible run human-triggered — moves into a step 1 gate that fires on the model-invoked path **only**: a run the user started by name asks nothing, and a run another skill or agent launched through the Skill tool stops once, names what is about to happen (a git worktree per ticket, each firing the repo's setup hook, agents running unattended under `--dangerously-skip-permissions`, branches merged back into the current branch), and waits. Declined or unanswered means nothing was run — never a partial run, never "just the DAG then dispatch". The gate is the first thing step 1 does, above the profile read, so a declined run has not written `docs/agents/delegate-profile.md` either. The prompt names the run's shape rather than a ticket count, since the tree resolves in step 2 and counting first would mean doing the profile work the gate exists to defer. Same trade as `pw-prove` (ADR 0005), for the same reason: `disable-model-invocation` is all-or-nothing across the unprompted and the chained path alike, and `skillOverrides` in `~/.claude/settings.json` is inert for plugin-sourced skills, so there is no narrower pin to reach for. The skill's `description` gained trigger phrasing, which the pin had made pointless — a pinned skill is absent from the model-facing listing, so nothing was ever matching on it
- `delegate-tickets` skill: **worker worktrees now get an explicit base.** Step 5 claimed workers were "branched off the current branch"; `orca worktree create` bases a new worktree on the *repo's default base* unless `--base-branch` says otherwise ("omit `--base-branch` to use the repo default base" — its own `--help`), so every worker was silently cut from `origin/main` while the skill's stated invariant said otherwise. Neither `delegate-tickets` nor the Orca-shipped `/orchestration` skill has ever passed the flag. Step 5 now passes it *and* verifies it took, in the same shape as the existing dead-worker check — a flag an older runtime ignores fails exactly like no flag, and the failure stays invisible until merge-back, where the branch drags in unrelated commits and the PR claims work it did not do. `hyrdrocks/nuxt-hyrd-chrysus#3116` shipped with exactly that, disclosed in its own body
- `delegate-tickets` skill: **amend means replace, never stack** ([ADR 0004](../docs/adr/0004-delegate-profile-amendments-replace-rather-than-stack.md)). Step 6 said only "amend the profile", which reads as *append a correction* — and did, producing a profile carrying two live baselines where the superseded one ("CLEAN baseline… any failure is a real regression") came first and in bold, and the true one ("the baseline above is STALE… known noise, do not re-triage") came second. A worker reading top-down concludes the opposite of the truth. Step 6 now requires the superseded fact be rewritten in place with git holding the history, exactly one baseline per check, and the fact filed in the field that owns it — the same amendment had filed a *dispatch* trap under **Post-merge check**, because that is where it was discovered rather than where it belongs
- `delegate-tickets` skill: **a profile is not an errata sheet.** When a merge-back disproves a claim in the repo's own `AGENTS.md` / `CLAUDE.md`, step 6 now says fix that file — same tree, same commit — rather than record in the profile that it is stale. A fact about another file is a fact with two homes and one of them rots; worse, the wrong doc stays wrong for everyone not running a delegation
- `delegate-tickets` skill: **`Worker constraints` splits into `Prohibitions` and `Conventions`.** One field had grown to ~30 bullets injected verbatim into every brief, roughly half of them repo conventions (i18n key ordering, component library, state management) that the repo's agent guide already owns and every worker loads anyway. Prohibitions are capped at ten and injected verbatim — each one something a competent worker would plausibly do, at the cost of a rerun or a corrupted sibling worktree. Conventions are a pointer, never a list. Thirty bullets is not thirty prohibitions in force; it is ten prohibitions and twenty pieces of cover. The five entries parked in `references/unmigrated-profiles.md` are deliberately left in the old shape — the file's own header calls itself a parking bay with dated baselines, and each entry is re-interviewed when it moves into its repo
- `claude-settings` skill: capture now warns that `skillOverrides` is taken verbatim from live settings and is **inert for plugin-sourced skills**, so an override naming a plugin skill gets captured while doing nothing — pin those with `disable-model-invocation: true` in frontmatter instead. Prompted by two such entries reaching the baseline in this same release
- `claude-settings` skill: captured this machine's `skillOverrides` into `baseline/settings.base.json`, adding `cypress-debugger` and `playwright-debugger` (`off`). Two entries the capture also picked up were dropped from both the baseline and the live settings, because `skillOverrides` is inert for plugin-sourced skills and neither did anything. `"e2e-reviewer": "user-invocable-only"` additionally recorded the opposite of the rule that `e2e-reviewer` must stay un-pinned, since it is the Step 6 handoff target of `pw-prove` and `playwright-test-generator`. `"playwright-test-generator": "user-invocable-only"` was redundant on top of being inert: that skill is already fully off via the `SKILL.md` → `SKILL.md.disabled` rename, which is the mechanism that actually gates discovery. `scripts/statusline.sh` was already identical to the deployed `~/.claude/statusline-native.sh`, so no script drift to reconcile
- `delegate-tickets` skill: repo profiles moved out of the skill and into the repo they describe, as `docs/agents/delegate-profile.md` — alongside the `issue-tracker.md` / `domain.md` / `triage-labels.md` that `/setup-matt-pocock-skills` already writes there, and summarised in that repo's `CLAUDE.md` under `## Agent skills`. A profile now versions with the code it constrains, is visible to anyone working in that repo, and can be amended by the coordinator mid-run
- `delegate-tickets` skill: step 1 discovery is presence-based rather than a lookup — the profile is in the repo or it isn't. `Remote` is demoted from match key to self-check, compared against `git remote get-url origin` and warned on mismatch, so a profile that arrived with a copied checkout is caught. A repo with no profile is interviewed **inline in step 1** rather than being sent to a setup skill, so a first run reaches the DAG
- `delegate-tickets` skill: step 6 amends the target repo's profile when a merge-back reveals a baseline, known-noise test, or environment trap it doesn't record — the capability the move unlocks
- `delegate-tickets` skill: ticket location is no longer a profile field. It lives only in `docs/agents/issue-tracker.md`, which step 2 already reads, so the two files cannot disagree

### Removed

- `delegate-tickets` skill: `PROFILES.md` deleted, with no central fallback — a two-tier lookup would make "which of these two is stale?" a permanent question. New: `references/profile-template.md` (the field schema an interview fills), and `references/unmigrated-profiles.md`, a temporary archive holding verbatim the profiles for repos not checked out at migration time. The skill does not read the archive; each entry is to be moved into its repo and deleted

## [1.3.0] - 2026-08-02

### Added

- Plugin-shipped hook (`hooks/hooks.json`, declared as `"hooks"` in the marketplace entry): `rtk.sh` on `PreToolUse(Bash)` → `rtk hook claude`, replacing the copy that lived in `~/.claude/settings.json`. One tracked copy now installs identically on every host instead of a settings blob hand-edited per machine

- The Orca, Superset and herdr hooks are installed per machine by their own tooling and stay in `~/.claude/settings.json`; the plugin deliberately does not ship them
- **Migration:** this fires in addition to anything still in `~/.claude/settings.json`. Delete the `rtk hook claude` entry there after enabling the plugin on a host, or the rewrite runs twice
