**That failure is not the mutation check's RED, and I refuse to read it as one.**

`RESTART=unproven` says the process answering 36495 is **not** the one I just started. The
`EADDRINUSE` line says why: the previous preview server did not die, so it still holds the port, and
my new process failed to bind and exited. `http://localhost:36495` answers 200 because the *old*
server is answering.

So the guarding test just ran against the **previous artifact** — the one built before the mutation.
Its failure is evidence about a stale server, not about whether the spec guards the change. The 128s
loading splash is the same story: the old bundle against a rebuilt backend state, not a slow
application to be waited out with a longer timeout.

**Fix the bring-up first:**

```bash
lsof -ti tcp:36495 | xargs -r kill
```

Then restart the preview against the freshly built artifact and re-run the serve phase with
`SERVE_RESTART=1` and a fresh `RESTART_LOG_OFFSET` mark, until it reports `RESTART=proven` and
`SERVE=ok`.

**Only then** do I re-run the guarding test, and I take the mutation verdict from *that* run.

What I do not do in the meantime: record a RED, write "the spec guards the change" on the strength of
this failure, or proceed to the revert-and-rebuild step. All three would be conclusions drawn from a
run whose server was never the one under test.
