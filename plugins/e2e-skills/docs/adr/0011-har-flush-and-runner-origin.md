# RECORD_HAR flushes on context close, and the runner's origin is pinned before the proof run

A rehearsal run of the revised pipeline (same repo, same change, from the same pre-test checkpoint as the run `docs/adr/0010` audited) finished in 21.6 minutes against the audited run's 57.7. The three losses 0010 targeted did not recur: no parallel-worker timeout, no clips destroyed by the mutation run, one `host-proof.mjs` call instead of five uploads behind a broken capture pipe, and a 2-second `hermetic.mjs` call in place of ~3 minutes of hand-written trace parsers. Two new defects surfaced, both of the same family the earlier audit kept finding — a documented rule that silently does nothing.

**`RECORD_HAR` had never written a file.** The probe's shutdown closed the browser and not the context, and Playwright flushes a `recordHar` on **context** close. So the recon pass reported clean, produced no HAR, and the spec fell back to hand-written `route.fulfill` mocks — the exact thing HAR-first mocking exists to replace. Nothing caught it because the failure mode is absence: no error, no exit code, just a missing file that the next step never asserts on. Reproduced against `example.com` in eight seconds once suspected; the fix is `await context.close()` before `await browser.close()`.

That fix is paired with a report, because the ordering alone would have shipped the same class of bug in reverse. On close, `RECORD_HAR` now prints either the path and byte count or a warning naming the consequence — *do not commit a `routeFromHAR` spec against a HAR that does not exist*. A recorder that cannot be observed recording is indistinguishable from one that is broken.

**The runner's origin is not the origin the agent verified.** The rehearsal's first proof run produced zero tests: `webServer.url` was the scaffolded `http://127.0.0.1:4000`, the dev server bound `[::1]` only, so Playwright saw no server, booted a duplicate, and died on `Timed out waiting 120000ms from config.webServer`. The agent had confirmed the server healthy — over `http://localhost:4000`, which resolves to `::1` and works. Two strings, one reachable, and the readiness gate checked the wrong one.

Step 3 therefore gains an item: read `webServer.url`/`use.baseURL` out of the config after env overrides and curl **that literal string**. Reachable → record `Runner origin:` in the Assumptions block. Refused while `localhost:$PORT` answers → a loopback-family mismatch, and the env var the config reads is carried on every runner invocation from Step 6 on. The Step-7 failure table gains the signature, next to 0010's: *every* test timing out on first navigation is a saturated server; **zero** tests running with a `config.webServer` timeout is this.

Trade-offs weighed. Making the probe fail hard on an empty HAR was rejected — a recon pass that legitimately triggers no matching API traffic is not an error, and a hard exit there would block honest runs; the warning plus the byte count gives the agent what it needs to judge. Auto-detecting the loopback mismatch and rewriting `webServer.url` was rejected as editing the user's config to suit our run, the same objection that kept the proof config static in `docs/adr/0008`. Verifying the HAR flush in CI with a real browser was rejected on cost: this repo carries no Playwright, so the guard in `scripts/ci/test-probe-har.sh` is structural — it asserts the close ordering and the presence of both report branches, and is itself verified by mutate-and-detect. The live flush is verified against a real app, which is how the defect was found and how the fix was confirmed.
